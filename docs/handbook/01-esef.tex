\chapter{ESEF filings}\label{ch:esef}

\section{Introduction}

Issuers whose securities are admitted to trading on a regulated market in the European Union have filed their annual financial reports in the European Single Electronic Format (ESEF) for financial years beginning on or after 1 January 2020 \parencite{EU.2019}. A report is an XHTML document that a person reads like any other annual report, and its figures -- from 2022 on, its notes as well -- are tagged in Inline XBRL against the ESEF taxonomy, the IFRS taxonomy with ESMA's additions. Every figure of the primary statements is therefore available as data: the concept it reports, the period, the unit, the dimensions such as the component of equity, and the value.

The reports are filed with the officially appointed mechanism of each member state, each with a site, a search and a format of its own. The repository filings.xbrl.org of XBRL International \parencite{XBRL.2026} collects them in one place, together with the reports of the United Kingdom and of Ukraine filed the same way, validates them, and publishes for each filing the report package as filed, the report in a viewer, and the facts it tags converted to xBRL-JSON, a plain JSON format for XBRL data. Module \emph{esef} of the \emph{fincommons} package reads the repository into two tables: one row per filing, and one row per fact.

The facts are keyed by the LEI of the issuer, which is the key of the entity master data of chapter \ref{ch:entitymasterdata}. A supervisor can thus put the balance sheet an issuer published next to what it reports under a reporting regime, and a reader can compare a figure across all issuers of a market without opening a single report.

The indexes and the reports are downloaded when the pipeline runs and never shipped with the package. The reports are the issuers' own publications, which they are required to make public. The repository states no licence for its copies; it provides its API free of charge, reserves the right to alter or withdraw it, and asks a client that uses it routinely to name a contact in its user agent, which the pipeline does where it is given one. The repository is not complete: a filing with technical errors may have no xBRL-JSON, and a filing whose LEI or date the repository cannot determine is not listed at all.

\section{Data pipeline}

\subsection{Landing zone}

There is no landing zone. The indexes and the reports are small enough to be held in memory while they are checked, and are written into the Bronze layer once they are known to be what was asked for.

\subsection{Bronze layer}

The Bronze layer keeps what the repository publishes, as it was published. The repository lists its filings in one index file per year of the period end, and asks a client that keeps a copy of the index to read these files rather than every page of its API, and to send the \verb|Last-Modified| of its last answer as \verb|If-Modified-Since|. The pipeline does both. An index that has not changed comes back without a byte, and every index of every year is kept, since together they are a few tens of megabytes and they are the catalogue of what there is to collect.

The reports are collected for the countries a run is asked for. A report is between a few hundred kilobytes and some tens of megabytes, most of it the notes, so the whole repository is a quantity a run should be asked for rather than one it collects by default. A report is downloaded when the Bronze layer does not hold it, or holds it from before the repository last processed the filing, which is what the repository does when it converts a filing anew. The report packages, the filings as they were made, are collected only where they are asked for, and are checked against the SHA-256 the index gives for them.

Every file is written under a temporary name and put in place once complete, and a record of each collection is written after the file it describes, so that a run that dies collects the file again rather than trusting a record of one that never arrived. An answer that is not an index or a report -- an error page sent with status 200 -- is refused before it replaces what the layer holds, and the addresses an index gives are refused where they leave the repository, since what they point to is written into the lake.

\subsection{Silver layer}

The table of filings lists every filing of the indexes, whether its report was collected or not: the filing, the issuer's LEI and name, the country, the period end, the language of the report, when the repository processed it, how its validation went and where its files are. It is a few tens of thousands of rows and is rebuilt in full on every run.

The table of facts holds one row per fact of every report collected. A fact has the concept it reports, the first and the last day of its period, the unit, the dimensions of the taxonomy as one text of sorted \verb|axis=member| pairs, and the value -- a number in \verb|value| where the fact has a unit, a text in \verb|text| otherwise. xBRL-JSON writes the end of a period as the start of the following day, so that a financial year to 31 March ends at midnight on 1 April; the table gives the day the period ends on, 31 March, so that it can be compared with the period end of the filing.

Text blocks are left out. Most of a report, by size, is its notes, tagged whole as text blocks with their markup: the note on intangible assets of one report is half a megabyte of HTML, tagged again for goodwill and for intangible assets and goodwill together. Whether a concept is a text block is a type of the taxonomy, which the report does not carry, but the value says so, and a value with markup in it is the note as the report presents it rather than a value to compare. The Bronze layer keeps the whole report, so a table of the notes can be built from it where one is needed.

The table of facts is partitioned by country and rebuilt country by country, for the countries whose reports changed, with the partition-wise write of the package's storage module that chapter \ref{ch:famafrenchdata} describes. A partition per filing would make each write smaller but leave the table in tens of thousands of directories of a few thousand rows each, which every query over it would have to open. Which reports each partition was built from is recorded in a mark beside the table, written after the partition is in place. The reports are read on the executors, one report at a time; a report that cannot be read is logged and counted, its country is written without it and left unmarked, so that the next run tries it again.

\subsection{Data quality}

The checks the figures are held to write what they found into a third table of the Silver layer, \emph{issues}, beside the filings and the facts. A check writes a row and leaves the figure where it is: nothing is dropped and nothing is corrected, and a filing with nothing wrong with it has no row at all. A run asked to check some countries replaces their rows and carries the others forward, which is how the pipeline collects. The machinery is shared with the module for the filings with the U.S. Securities and Exchange Commission and the one for the Japanese EDINET system; what is particular to ESEF are the nineteen checks themselves, read from the concepts of the IFRS taxonomy.

The checks that matter most are the arithmetic ones, the relations a statement states on both sides: total assets against the current and non-current assets and again against equity and liabilities, revenue against the cost of sales and the gross profit, the result before tax against the tax and the result, and the three cash flows against the movement in cash. They are run over the facts without dimensions only, since a figure broken down by segment is a part of a total and not a total. Each identity is the one the standards state, not the one a statement would show if every issuer laid it out alike, and the difference is where most of the work went. The three cash flows sum to the movement in cash \emph{before} the effect of exchange rates on the cash held, which IAS~7 presents on a line of its own; the check reads that movement where it is tagged and otherwise takes the effect off the movement after it, and it accepts the movement as tagged as well, since some reports put the movement before the effect under the concept for the one after it and their figures agree. The assets held for sale may stand below the current assets rather than among them, under either of the two concepts the taxonomy has for that line, and a gap of exactly their size is not a gap. The result of discontinued operations falls between the result before tax and the result for the year, and the share of the profit of associates may as well, where an issuer presents it after the tax. Two checks look for a figure stated twice. One figure tagged with two values is a fault only where the values disagree as XBRL compares duplicate facts -- each stands for the interval its decimals allow, so 673.3 million in the statements and 673 million in the notes agree. And one period filed twice in one language is a correction, and a warning, only where the copies state different facts; where every copy states the same facts the repository has received one report twice, which a note records without faulting it. Two checks read the table of filings rather than the facts, because the repository publishes what a mechanism of a member state does not: it validates every filing and publishes the count of errors, and it lists filings whose xBRL-JSON it could not produce. Their rows can therefore name filings whose facts the lake does not hold. One check says nothing is wrong at all: a report that tags more than half its figures with concepts of the issuer's own making is not faulty but hard to compare.

What each code means, how severe it is and what to do about it is a row of a catalogue shipped with the package, \verb|dataquality_checks.csv|, rather than a branch in the code. A deployment with checks of its own ships a catalogue of the same shape. The checks were run over six annual reports of voestalpine, for the financial years to March 2021 through 2026, and found nothing in their figures; getting there corrected one check, since the identity of the result before tax, the tax and the result does not hold without the discontinued operations that fall between those lines. Run over the Austrian and Dutch reports of the lake in November 2026, the checks named reports whose figures were sound, and each case was read before the check was changed. Of the 72 reports found with cash flows that did not sum, 59 were out by their exchange differences alone; of 12 asset splits, 9 were explained by the assets held for sale, among them TenneT's German business of 27.6 billion in 2023, and the three left are Österreichische Post's, which presents the assets of bank99 as a block beside the current and the non-current ones; all four results that did not reconcile were ASML's share of Carl Zeiss SMT and one other share of associates presented after the tax; 156 of 196 facts tagged twice with two values were one figure at two precisions; and 42 of 77 filings of one period filed twice were copies, most of them added to the repository within minutes of each other. What the arithmetic checks still find are mostly figures on the wrong line: a bank whose movement in cash is tagged as 31 thousand against cash flows of 972 million, or a balance sheet whose liabilities are tagged with the total of equity and liabilities.

\subsection{Gold layer}

There is no Gold layer yet. The natural first table is one row per issuer and financial year with a selection of figures of the primary statements -- total assets, equity, revenue, profit -- in one currency, which needs a rule for which of several filings of the same report counts and a conversion with the exchange rates of chapter \ref{ch:exchangerate}.

Until there is, the report templates of the module do in R what that table would do, each for the question it answers, and each states its rule. They read the Silver tables as Parquet and are rendered with Quarto to PDF:
\begin{itemize}
	\item an \emph{analyst factsheet} on one issuer, its statements, indicators and texts over the years it filed, and its latest year beside the other issuers of its market -- each issuer's financial year ending in the twelve months up to the issuer's own, banks and insurers set apart, every figure derived alike from concepts of the IFRS taxonomy alone, and no median shown for an indicator fewer than ten of them could be computed for;
	\item a \emph{sector factsheet} on a panel of issuers, each year beside the years around it and beside the market it was filed in, which can reach past ESEF to issuers filing with the Commission or on EDINET where the combined tables of the lake hold them;
	\item a \emph{coverage report} on what the repository lists and what the issuers tagged, and so on how many issuers a factsheet could be built for;
	\item a \emph{quality report} on what the checks found across the whole record, every rate taken over the filings with facts, since only those were asked every check;
	\item two \emph{country factsheets} that take a country and nothing else. One ranks the issuers whose figures to check first: each check scores once per issuer and year, and six screens set an issuer's reports side by side to find restated, rescaled and sign-flipped figures, a stray currency, and a report that names another entity than the one of its LEI. Where an identity does not hold it gives the two sides and the gap with its share of total assets or revenue, so that a line left out can be told from a figure on the wrong line, and it does not hold a bank or an insurer -- an issuer that presents one of their lines, a bank's loans to other banks or its customers' deposits among them -- to a revenue line or to the split of its assets into current and non-current. The other describes what the country's listed companies reported -- revenue, results, margins, returns and cash -- with growth taken like for like from each report's own figures for the year before, banks and insurers kept apart, a group reported by both a listed holding and its listed subsidiary counted once, and the reports the identity screen catches left out.
\end{itemize}
Beside the templates there is one call that writes data out rather than a document: it exports the reports of a single issuer to an OpenDocument spreadsheet, with the filings set side by side -- one row per figure and period, one column per filing -- so that the same field of different reports is read across a row and a figure a later report restates shows as a row holding two values. Nothing is converted and nothing is corrected there either, and the unit of every figure stands beside it, since an issuer that changed its reporting currency has two units in one row. On the seven filings of PORR AG in the lake the sheet is 953 rows, of which 182 differ between the filings that state them: 167 of those are the two filings for 2024, the same report re-received thirteen days later, whose figures are a thousandfold apart.

No template writes back into the lake. Each reads the population it describes, says which it is, and refuses a Silver layer in Delta, since a Delta table keeps the files it has replaced until it is vacuumed and Parquet read directly would count them.

\section{Software architecture}

Module \emph{esef} is organised along the layers of the pipeline. The part \emph{common} declares the layout of the data lake and the schemas of the tables and opens them; \emph{parse} reads an index into filings and a report into facts, in plain Python, so that it can be tested on its own and run on the executors as it is; \emph{bronze} collects the indexes, the reports and the packages; \emph{silver} builds the two tables; \emph{quality} holds the checks and builds the table of issues; \emph{export} writes one issuer's reports out as a spreadsheet; and \emph{pipeline} runs the whole in one call, \verb|update_esef|. A scheduled run is a script around that call,
\begin{quote}
\verb|esef.update_esef(spark, "paths.yaml", ["AT"], contact="me@example.org")|
\end{quote}
which takes the countries to collect -- and, with \verb|contact|, the contact the repository asks for -- but no argument saying what changed: that is read from the repository and from what the lake already holds. No module of the package opens a Spark session; the session is the caller's, so that the same pipeline runs on a cluster that has one and on a workstation that has to say how much of itself to give it. The checks are a call of their own, \verb|update_silver_esef_quality|, made after the pipeline has run, and the report templates live beside the code in the folder \emph{templates} of the module.
